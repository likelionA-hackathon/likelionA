# Notion 연동 준비

## 왜 이 문서가 중요한가

AI 요약의 품질은 **원본이 얼마나 지저분한지**에 달려 있습니다.

원본이 이미 잘 정리된 요약이면 AI가 할 일이 없습니다. "요약을 요약"하니 결과가 밋밋해지고,
심사위원은 "이거 그냥 복사한 거 아니에요?"라고 묻습니다.

반대로 **퇴근 직전에 급하게 쓴 진짜 인수인계 문서** — 시간순으로 뒤섞이고, 결론이 중간에 묻혀 있고,
담당자가 안 적혀 있고, "아 그리고"로 시작하는 문단이 붙어 있는 문서 — 를 넣으면
AI가 그걸 요약/변경사항/맥락/추가확인으로 갈라내는 게 눈에 확 보입니다.

**그래서 아래 샘플은 일부러 지저분하게 썼습니다.** 다듬지 마세요.

---

## 1. 데이터베이스 만들기

Notion에서 새 페이지 → `/database` → **Table - Full page**
이름: `인수인계`

### Property 설정

| 이름 | 타입 | 값 예시 |
|---|---|---|
| `이름` | Title | (기본으로 있음) |
| `우선순위` | Select | `Critical` `P1` `보통` `backlog` |
| `담당자` | Text | 이름 |

우선순위 옵션은 **일부러 표기법을 뒤섞어 두세요.** `Critical` / `P1` / `보통` / `backlog`.
이걸 우리가 `긴급 / 높음 / 보통 / 낮음` 하나로 통일하는 게 데모 포인트입니다.
심사위원이 "Critical이 왜 긴급이죠?" 물으면 화면 툴팁에 `원본 표기 "Critical" → 긴급` 이 떠 있습니다.

> property 이름은 `우선순위/priority/중요도/긴급도`, `담당자/작성자/assignee/owner` 중 아무거나 인식합니다.

### 페이지 1 — 우선순위: `Critical` / 담당자: `전철우`

**제목:** `PG 교체 관련 인수인계`

```
8/12 새벽 배포 끝났고 일단 결제는 나이스페이로 다 넘어갔음.

오늘까지 한 것
- 승인/취소 API 전부 나이스페이로 교체
- 02:00부터 신규 결제는 100% 나이스로 나가고 있음. 지금까지 실패 0건
- 어드민 결제조회는 아직 안 봤음

빌링은 아직임. 토스 빌링키를 그대로 못 옮겨서 마이그레이션 스크립트 짜는 중인데
9월 첫째주는 되어야 끝날 것 같음. 그때까지는 정기결제만 토스, 나머지는 나이스로 이중 운영.

아 그리고 중요한 거 하나. 취소 API 응답이 다름.
토스는 부분취소하면 remainingAmount를 내려줬는데 나이스는 안 줌.
그래서 정산 배치에서 잔액 검증하는 부분이 지금 그대로면 부분취소 건은 전부 실패함.
승인금액에서 누적취소금액 빼서 직접 계산하는 걸로 바꿔야 함.

결제 고유번호 포맷도 바뀜. tosspay_xxx 였는데 이제 np_xxxxxxxx 임.
고객센터 조회화면에 정규식이 하드코딩되어 있는 걸로 아는데 그거 확인 필요.

웹훅은 /webhooks/nicepay 로 새로 팠음. 재시도 정책이 5회 지수백오프라
같은 이벤트가 여러 번 올 수 있음. 우리 쪽은 dedupe 넣어놨는데 정산 쪽도 필요할듯.

그리고 8/12~8/13 이틀치는 두 PG에 섞여 있어서 자동 대사가 안 될 거임. 수기로 맞춰야 함.
근데 이게 승인일 기준으로 볼지 매입일 기준으로 볼지를 안 정했음. 두 PG 매입시각이 달라서
기준 안 정하면 양쪽 리포트가 계속 안 맞을 거임. 이건 정산팀에서 정해주면 좋겠음.

토스 정산 리포트 일배치는 9월 첫째주에 지울 예정인데 빌링 이관 끝나기 전에 지우면
정기결제 정산이 비니까 순서 지켜야 함.
```

### 페이지 2 — 우선순위: `P1` / 담당자: `전철우`

**제목:** `정산 배치 시간 옮김`

```
나이스 매입 확정이 새벽 4시 넘어서 떨어짐. 기존 03:00 배치로는 전날 건이 안 잡힘.
그래서 05:30으로 미뤘음. 리포트는 06:30에 나오는 걸 목표로 잡았는데 아직 실측은 안 해봤음.

이거 때문에 오전 회의용 정산 대시보드도 07:00은 되어야 최신값이 뜸.
운영팀이 6시반쯤 보는 걸로 아는데 그때 들어가면 빈 화면 볼 것 같음. 공지 필요.

배치 실패하면 #settle-alert 로 슬랙 알림 가게 해놨음. 근데 지금 수신자에 결제팀만 있음.
정산팀 온콜도 넣어야 할 듯.

재시도는 일단 안 넣었음. 매입 데이터가 덜 들어온 상태에서 자동 재시도 돌리면
같은 실패만 반복할 것 같아서. 이건 어떻게 할지 정해야 함.
```

### 페이지 3 — 우선순위: `보통` / 담당자: `김건희`

**제목:** `환불 문구 교체 (약관 개정)`

```
9/1 약관 개정 발효라서 그 전에 사용자 노출 문구 다 맞춰뒀음.

바꾼 곳
- 결제 완료 페이지
- 마이페이지 > 주문내역
- 환불 안내 이메일 템플릿

내용상 바뀐 건 환불 처리기간 안내가 "영업일 3~5일" 에서 "영업일 5~7일" 로 늘어난 거 하나임.
정산 계산 로직은 안 건드렸음. 문구만.

이메일 템플릿은 스테이징까지만 반영했고 운영 배포는 8/28 예정.
CS 응대 스크립트도 같은 문구로 맞춰야 하는데 그건 아직 안 함.
```

### 페이지 4 — 우선순위: `backlog` / 담당자: `전철우`

**제목:** `결제 실패 로그 정리하면 좋을 듯`

```
PG마다 실패 사유 코드 체계가 달라서 로그가 파편화되어 있음.
장애 볼 때마다 PG별 코드표 찾아보느라 시간 걸림.

공통 failureReason enum 만들자고 제안만 해둔 상태. 구현은 안 했음.
급한 건 아닌데 나중에 실패율 대시보드 만들 거면 먼저 정리하는 게 쌀 것 같음.

이걸 정산팀이 가져갈지 결제팀이 계속 들고 갈지는 안 정했음.
```

## 3. 연동하고 돌리기

`.env` 에 넣고:

```
NOTION_TOKEN="ntn_..."
NOTION_DATABASE_ID="32자리해시"
GEMINI_API_KEY="AIza..."      # https://aistudio.google.com/apikey (무료, 카드 불필요)
```

서버 재시작 후 (`<페이팀ID>` 는 seed 로그에 찍힌 값):

```bash
curl.exe -X POST http://localhost:3000/api/workspaces/<페이팀ID>/connections ^
  -H "Content-Type: application/json" -H "x-baton-user: cheolwoo@baton.dev" ^
  -d "{\"provider\":\"NOTION\",\"token\":\"ntn_...\",\"databaseId\":\"32자리\"}"

curl.exe -X POST http://localhost:3000/api/workspaces/<페이팀ID>/notion/sync ^
  -H "Content-Type: application/json" -H "x-baton-user: cheolwoo@baton.dev" ^
  -d "{\"limit\":4}"
```

`target` 기본값이 `partner` 라, **페이팀이 동기화하면 정산팀 대시보드에 인수인계가 꽂힙니다.**
그게 "앞 팀이 넘긴 걸 뒤 팀이 받는" 데모 흐름입니다.

## 흔한 실패

| 증상 | 원인 |
|---|---|
| `NOTION_AUTH_FAILED` | 토큰 오타, 또는 **integration 을 DB 페이지에 초대 안 함** (⋯ → 연결) |
| `NOTION_NOT_FOUND` | databaseId 가 틀림. `?v=` 앞 32자리만 |
| 페이지는 오는데 본문이 빔 | DB 안의 **행(페이지)** 이 아니라 DB 자체를 가리켰을 수 있음 |
| 우선순위가 전부 `보통` | Select property 이름이 인식 목록에 없음. `우선순위` 로 바꾸세요 |
| 요약이 밋밋함 | 원본이 너무 깔끔함. 위 샘플처럼 날것으로 |
